# 41-browser-group-reorder

Move one **active physical group one place** on the selected browser board. An Owner opens the heading's **Group menu → Move group up** or **Move group down**. The menu closes and the choice submits immediately. Disable Up on the first group, Down on the last, both on a sole group, and both for Member and Viewer. Opening, dismissing or activating a disabled choice sends no write. Preserve the heading's double-click editor, menu edit/archive actions and item grips. The reference also accepts a non-touch drag from a **group name** across sections, before or after a heading's midpoint; it uses the same order command but has separate hit-testing, cancellation and click suppression. Leave that gesture for a subsequent packet.

**Compared fixture.** Board 201 is at revision 7. In `(position,id)` order its active groups are **A** = `g-old` (Work at 3, root 59), **B** = `g-z` (Work at 3, roots 61 and 63), and **C** = `g-end` (Reserve at 12, empty). Groups start at revision 1. Each root is named Ink. Root 67 in B is individually archived. Archived `g-hidden` at 20 contains 57; board 202 has `g-peer` with 62. The reference also has a nested child of 61; it stayed there. Use existing root storage for the preview.

| Menu action | Visible order, request and independent readback |
|---|---|
| Open the second Work's menu and choose Up. | Submit `[B,A,C]` at board/7. Reload shows `B [61,63], A [59], C []`. Positions are **0,1,2** and **all three** active group revisions are 2, including the empty bystander; board/8. Invisible and foreign rows are unchanged. |
| Move B down but refuse the transaction at commit. Then remove the fault and choose Down again. | First attempt leaves the complete /8 state intact. A fresh action with `[A,B,C]` at /8 commits /9, all three groups at /3. Dense positions remain; the original sparse positions are not restored. |

No retained order is submitted. Reopen B's menu and choose Up: now the neighbour is **C**, so `[A,B,C]` at /10 commits /11, all active revisions /5. |

**Command boundary.** One preview-only `POST /preview/api/navigation/boards/{board}/group-order` with `{board_revision, group_ids}`. One named Rust operation owns acceptance. Submit the complete ordered array of board-local IDs from the accepted grouped snapshot, including empty active groups. Under current selected Owner access, lock the board, check the positive expected board revision, then check an exact permutation of this board's active, non-deleted IDs. Missing, duplicate, archived, deleted, unknown or foreign-only IDs conflict; never sort, deduplicate, append leftovers or resolve by label. Bound the body and membership read using the existing preview limits; never reorder a truncated set. Atomically write zero-based positions in request order, increment **each included group's revision once** even if its position already matches, and advance the board once. A direct complete permutation at the current baseline is valid, including the already accepted order. Repeating it at the stale baseline conflicts. No per-group revision inputs, receipts, migration, item writes, column order or generic structure endpoint.

Keep the accepted grid and counts visible until commit and authoritative refresh; allow one submission at a time. On known failure show the refusal and allow a fresh deliberate action. On 409, uncertain acknowledgment or failed post-commit read, offer **Reload board**; it only reads. Recompute any next move from the latest ordered IDs. Never replay a stale array or silently apply the old direction to a new neighbour. 403 rechecks current board access; 401 returns to sign-in. Ignore late completions after leaving the selected board/session. These explicit recovery controls are preview requirements; the compared table reported the error and recovered via document reload and a new menu choice.

**Required gates.** Check actual enabled states, menu clicks, request counts, arrays, board revisions and responses in owned headless Chromium. Inspect rendered group IDs, counts and child order independently of both grouped/flat reads and fresh DB snapshots of board/group/item/receipt rows from both boards. For access changes distinguish the intended grant/session edits from structural changes.

- `browser_moves_group_one_place_from_menu`: first/last/sole boundaries, dismissal, both directions on duplicate names and an empty neighbour. Hold the board lock on submit: no second write or speculative order. Refresh/reload must retain accepted IDs, counts and child order.
- `browser_reloads_order_before_moving_group_again`: deferred commit failure and fresh retry, peer move while menu is open, 409, reload without writing, deliberate move past the **new** neighbour as above. Fail the accepted move's refresh once; Reload reads the committed order without another POST. Check the rollback snapshot before removing the fault.
- `browser_demoted_owner_cannot_reorder_groups`: demote after opening an enabled menu. One attempt returns 403; the authorized reread removes both move permissions. Member and Viewer still differ on item editing. Test withdrawal of membership and session revocation; neither exposes or changes protected order.
- `preview_group_reorder_requires_current_owner` (`loopback_board_access`): cover missing/revoked session, Member (including creator), Viewer and Owner, selected board/workspace grants and states, wrong method and route isolation. The menu is not an access check. A same local ID on a different board cannot be changed by the command.
- `preview_group_reorder_checks_active_permutation_and_commit` (same suite): malformed input, nonpositive/stale baseline, omitted/duplicate/inactive/foreign-only/unknown IDs and bounded reads; include a same-order current-baseline request. Race two different valid orders at the same revision: one commits, one conflicts. Replay the winner at its old revision. Refuse a deferred commit and prove all ranks and revisions roll back. Reconnect; compare group and flat reads and immutable fields/rows, including individual archives, children of inactive groups and receipts.
