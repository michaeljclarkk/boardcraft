# 31-browser-board-groups

Open the last `Review` from the signed-in browser list. On the default table, display the **physical groups of that board**, including active empty groups. Render a named section and heading per group with the count (`No Items`, `1 item`, `2 items`); put the existing item-name controls inside the corresponding section. Neither a group name nor an item spelling is unique. Keep the plain board URL, the selected item UUID on rename, and the current session. This slice covers expanded groups and active top-level items with explicit manual positions; it does not introduce group mutation controls.

**Reference comparison (synthetic).** The board metadata read orders groups by position then stable group ID and separates inactive groups. With no view filter or derived grouping, the table maps these active groups in that order, even when the root count is zero. The group-page operation checks the selected board and active group and orders active roots by source position (nulls last), creation time, then item ID in the unsorted Main view. Children are not separate root rows. The table associates those pages by group ID, not title. The following fixture ran through the reference destination, board and group-page operations against disposable PostgreSQL as a subscribed Member in a closed workspace. Its accepted metadata and rows also ran through the actual table and viewport hook in an isolated headless browser with a local page adapter and stand-ins for unrelated controls. This is component plus operation evidence, not a deployed sign-in-to-grid test.

The reference showed `Work / 2 items`, `Reserve / No Items`, `Work / 1 item` and only the corresponding UUIDs. Saving ` Coral ` on 59 returned `Coral` on reread, revision 2; the two other visible rows on 201, the archived row and 202 stayed unchanged on independent DB readback. Targeting the archived group's page was rejected, as was a valid name change on 57. Removing only workspace membership made 201 unavailable; restoring it reopened the same groups. Use the same inputs for boardcraft; insert in a different order from presentation.

**Implementation boundary.** Add a versioned transactional [board-store migration](../crates/board/src/store.rs) for durable board-scoped group membership, group identity, heading, position and active state. Prevent dangling/cross-board item assignments in PostgreSQL. For pre-group boards and future flat `create_board` snapshots, define a stable compatibility group for existing rows; preserve original item IDs, spelling, order and revisions without fake rows or a rewrite on read. Keep an empty pre-group board readable and empty. Record the compatibility choice separately from reference behavior. Allow two groups to have equal positions (tie by ID) and two different groups to start their items at zero. For this slice, unique explicit item positions *within a group* suffice; imported nullable/tied item positions remain open.

Return one complete grouped result on the existing **browser transport** `GET /preview/api/navigation/boards/{id}`. Keep the native bearer `GET /navigation/boards/{id}` and scoped reads flat (same item wire type); do not change the public document route. Use [the existing handler and access decision](../crates/mobile-edit-host/src/lib.rs) for both shapes: authorize SelectedRead in the same transaction as the rows and the edit hint. Use a consistent ordered read restricted to the requested board, including empty groups; do not fetch a board per group, scan all boards, or assemble a board from independently authorized requests. Bound the small-board projection; if over its documented limit, show an explicit unavailable/unsupported result, never a silently partial grid or false counts. Preserve active-group visibility on the flat surfaces too. Reuse the conditional rename: the server must check that the addressed item still belongs to an active group of the authorized board **at write time** (lock the supporting rows through commit). Inactive membership must not disclose a saved row or change any revision. No independently callable group write/move API, client-side grants or second name writer.
