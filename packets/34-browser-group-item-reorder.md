# 34-browser-group-item-reorder

In the selected board's unsorted physical grid, drag **one root by its grip** within its group. This is a primary-pointer gesture: at 6 CSS pixels of movement the row starts dragging; above the target row's midpoint means **before**, below it means **after**. Mark the drop edge without moving the saved rows. Release once to submit. A short movement, Escape during drag, pointer cancellation, dropping on self or outside a valid same-group row sends nothing. Consume the drag's release click so it does not open the name editor or menu. The reference has no keyboard item-reorder command; Escape cancels. Keep existing name editing and the separate [Move to dialog](33-browser-group-item-move.md) intact.

**Reference fixture and result.** Use board 201 and the group identities from [31](31-browser-board-groups.md). For this case only, the first `Work` (`g-90`) contains `73 Sketch@0, 61 Ink@10, 67 Ink@30, 77 Fold@40`, where `@` is the stored position. `g-10 Reserve` is empty, the last `Work` (`g-20`) has `59 Ink@2`; 57 in an archived group and 62 on board 202 remain outside the grid. Board and item revisions start at 1. Grip the **second Ink in the first Work** (67); release over the **upper half of 61**. Counts remain `4 items`, `No Items`, `1 item`. Immediately after the authorized refresh and after document reload:

|---|---|---|

Unselected siblings retain relative order, revisions, field stamps, names, groups and creation provenance; **their numeric positions can change**. Other groups and boards keep even their numeric positions. Nothing is deleted or recreated. The mounted reference table, pointer handler and actor-scoped operation ran on a synthetic disposable database in headless Chromium: short travel and Escape sent nothing, both drop edges persisted across reload, demotion before release was denied, and a deferred receipt failure rolled back even the sibling position updates. Fresh reads also distinguished an identical replay from conflicting operation reuse, stale revisions and a foreign-group anchor. The comparison used a local transport/refresh adapter, not the full signed-in reference shell.

**Write contract.** Add a matched-browser-only `POST /preview/api/navigation/boards/{board}/items/{item}/reorder`. Supply a fresh operation UUID per deliberate drop, the displayed board and selected item revisions, the group ID, and one anchor UUID with side `before` or `after`. No labels, actor, client-computed position/list or new destination group. Return an acknowledgment of committed identities, not a guessed row order. Expose the board revision alongside the existing grouped GET (e.g. a header from the same consistent read); retain its array shape, size limit, access hint and native flat contract.

One named [board store](../crates/board/src/store.rs) operation owns the order. In the current authorized write transaction, serialize against other reorders and existing create/group-move writers. Require an active group on the selected board and an existing source and distinct active anchor **in that group**. Compare exact, positive board and selected item revisions (a selected-row rename invalidates a drag). Under lock, read ordered sibling identities by the existing position, creation and UUID rules; remove the selected root, insert it relative to the anchor and persist dense zero-based positions for the whole group. Bound the identity read, never rank a truncated visible subset. Set positions together without a per-sibling query or unrelated data writes. Increment the board revision, selected revision and both selected field stamps as above. An old group-edit baseline cannot cross this reorder; an unselected sibling's name baseline still works. Migrate populated v5 without rewriting existing order, history or provenance. Do not retrofit unrelated edits into board-structure writes.

Persist a receipt for the operation UUID in the **same transaction**. Under current authorization, identical actor/board/item/group/anchor/side and baselines replay the original acknowledgment without checking now-stale revisions or applying order twice. Changed content or another actor cannot claim it. Two different operations from one board revision must not both commit. Return conflicts for stale revisions or a lost/moved anchor, without disclosing another board's rows. No receipt on denial, validation failure, conflict or commit fault. Do not reuse the single-field group save: it preserves positions and has different revision semantics.
