# 40-browser-group-edit

Edit the name and colour of **one existing active physical group** on the selected browser board. A single click on the heading name does nothing; an Owner's double-click opens **Edit group**. **Group menu → Rename group** and **Change group colour** open that same dialog with both fields. Even the colour action focuses **Group name**, initially showing the accepted spelling with the caret at its end. The heading never becomes an inline name input. Use the existing group menu, keep Archive working, and share the dialog fields with Add group where their meanings match. Opening an edit must preserve any stored six-digit colour, including one outside the create palette.

**Compared fixture.** Board 201 starts at revision 7. Its active groups in `(position,id)` order are `g-old` (Work, position 3, root 59), `g-z` (Work, 3, roots 61 and 63), and `g-end` (Reserve, 12, empty). Root 67 in `g-z` is individually archived. Archived `g-hidden` at 20 contains 57; board 202 has `g-peer` with root 62. All roots are named Ink; groups start at revision 1 and colour `#443322`. Target the **second Work by ID**. The reference also has a subitem under 61; it remained there. Do not introduce subitem storage for this browser slice.

**Command boundary.** One preview-only `PUT /preview/api/navigation/boards/{board}/groups/{group}` and one named Rust edit operation. Use the existing board-local key (including `main` and imported group IDs), v10 columns and selected Owner authorization. Expose the positive group revision alongside each group in the bounded grouped read, from the same snapshot as the board revision. Reuse create's stored-name/colour rules: trim, 1–160 UTF-16 units, six hex digits after `#`; create's *proposed UUID* rule is not an existing-ID rule. Hold access and board locks through commit; require an existing active group on this board and both matching positive revisions. Update only name, colour and the two revisions, even when the values compare equal. Position, lifecycle and items are not edit inputs. No migration, receipt, upsert, reorder or flat/native contract change. A same-named or same-ID group elsewhere cannot satisfy a miss here.

Keep one request in flight; show the old grid until commit and authoritative reread. On 409 retain the draft and both baselines until the user reviews and explicitly adopts. Never substitute a group by label or fall back to revision zero when the original group has disappeared or become inactive. On a known rejection keep a correctable draft. If acknowledgment is uncertain or the post-commit GET fails, offer a **read**, never an automatic second write: the continued existence of an edited ID does not prove this request committed. Show the accepted fields/revisions before any deliberate new edit. Guard late completions by board/session; 403 rechecks selected access, 401 returns to sign-in. These are preview recovery requirements. The reference's generic save accepts more than its active-group UI exposes; updates to inactive groups and other structural fields are outside this route.

One observed difference matters for recovery: when a peer archived the open target, the reference dialog allowed adoption of a snapshot without it. Its next save sent baseline zero and acknowledged the existing archived ID without applying the draft. The preview must instead tell the user the target is no longer available.

**Required gates.** Drive actual pointer and key events in owned headless Chromium. Record request path, count, fields, baselines and status; check rendered IDs, order, counts, labels, colours, dialog values and focus independently of a fresh DB read. Compare complete group, item and receipt rows on both boards, plus session and grants. Keep checks for the archived and foreign children that cannot appear in the active grid.
