# 11-windows-failure-reopen

Restore a **submitted, failed** Windows name change after remount or fresh process launch. Client-local recovery belongs to a stable actor and board, not a display name, view, database credential or access grant. Supply an explicit local actor context until sign-in exists; do not share a fallback identity between users. Preserve the row ID, raw spelling and failure reason separately from the board's accepted titles. Show the normal parent failure actions with no open editor, projection or automatic submission. Never save an unsubmitted draft or pending request in this failure store. Use only validated, scoped data; do not overwrite unreadable recovery silently or delete a newer failure with a stale dismissal. Report the reference lifetime and limits, including any remaining independent-window and unreadable-data UX gaps.

Gate: `windows_smoke::failed_name_reopens_only_for_actor_and_board`, with the three earlier Windows cases run serially. Drive real controls in fresh processes with an isolated shared recovery directory. Fail the second of two `Review` names (IDs 42 then 17). Reopen as another actor and on another board and show clean accepted rows, zero submissions. Return to the original scope and show accepted names and the retained failure with zero submissions; an independent fresh connection checks both IDs/order, names and revisions before any further action. Explicitly retry a fixture-faulted padded ` Coral ` after removing the fault; check the exact raw pending spelling, one submission, `Review`/1 while locked, then `Coral`/2 and no failure on reopen. Also restore and dismiss a failed request, without writing, and prove dismissal survives another process. No real user data, Android rebuild or new script. Coordinator owns the synthetic reference comparison and runner; worker updates Rust, affected docs and handoff only. Do not commit or push.

The reference removes a superseded failure on submission, before the save settles, and records it again only on rejection. While the explicit retry is blocked by the row lock, open a fresh same-scope process and assert accepted `Review`/1, no actions and zero submissions there before releasing the lock. Corrupt recovery must preserve its bytes and show a warning without hiding the accepted board. A repair/discard UI for unreadable data is a separate workflow.
