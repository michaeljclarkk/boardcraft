# 37-browser-root-archive-restore

On a selected physical board, archive the **second Ink in the first Work** from its row menu, reopen the board's Archive, and restore that same root to its old place. Use a synthetic signed-in **Owner** with access to this board and workspace. Member edit access, creating the board, checking the row, knowing its ID or opening the archive address does not authorize either transition.

**Compared fixture.** Start with [34's seven roots](34-browser-group-item-reorder.md), board and item revisions 1. Add root 68 `Trash only` (Deleted) and 69 `Staged` (Staging) in `g-90`, both at position 1. Root 57 is itself Active in the Archived `g-30 Retired`; 62 belongs to board 202. Persist these distinctions: the reference's item states are Active (0), Archived (1), Deleted (2) and Staging (3). Ordinary reads require an Active item in an active group. Recovery uses *effective* state: Deleted on the item or an ancestor takes precedence over Archived; otherwise the root is not in either recovery list. Staging alone belongs in neither list nor the grid. Never implement Archive as a DELETE, a group change, or a generic `!active` predicate.

Use a named single-root operation with exact board/item revision, own source state, board identity and active group checks. Commit state, the two revision increments and one actor/board/command-bound receipt together. Exact replay acknowledges the original ID without another change. Cross-action or existing move/reorder receipt collisions conflict. In the reference the generic Restore command also handles Trash and does not require an archived source; even a fresh Restore on Active advances revisions. **This board Archive action** offers and accepts only own Archived → Active. Do not expose arbitrary state assignment. Preserve all rows, original creation metadata and old receipts on upgrade. **Preview transport.** Under `/preview/api/navigation/boards/{board}`, use GET `archive` for the inventory and POST `items/{id}/archive` or `items/{id}/restore` for one command. The path binds the target; the request carries the operation UUID and expected board/item revisions, not an actor, role or destination. Distinguish 401 (sign in), 403 (recheck access), 409 (stale baseline or mismatched receipt), unavailable item/invalid transition and an unexpected store fault. The archive document address itself performs no mutation.
