# 14-loopback-board-access

Protect the existing single-board loopback host. On **every** board read and name save, resolve the caller's in-memory bearer at the host using the packet 13 account operation, then check access for that account and the requested board. A known board UUID, item UUID, local actor selector or client-supplied role is not a grant. Translate the approved reference's access rule for the scoped Viewer and Member; record unmodeled board kinds or roles separately. A Viewer with read access sees the ordered board but cannot rename. A Member with edit access can use the existing conditional name operation. Distinguish missing/rejected sessions (401; sign in again), authenticated write denial (403; no retry as the same Viewer), and an unavailable account store. Do not add a new login endpoint or change the session lifetime contract to exercise rejection.

For the scoped access comparison, use a private board in an open workspace. A Viewer or Member must be the board creator or a subscriber to see it. Read access alone does not authorize a Viewer to write. Closed-workspace membership is a separate prerequisite in the full product; do not infer visibility from a board UUID alone. Deny absent policy data by default.

Gate: `cargo test --locked --workspace --test loopback_board_access`. Require both enabled cases against the production handler over loopback and a fresh schema per case in `rustday_test`:

- `viewer_reads_but_cannot_rename`: sign in a synthetic Viewer with access to one board; read two distinct `Review` rows in order. Attempt a valid rename of the second row, require typed permission denial, then independently reconnect and read both original IDs, titles and revisions. Revoke that session: the same client now gets session rejection on read and rename, not permission denial. Check both rows again. Requests without a bearer cannot read or rename.
- `member_edits_within_scope`: sign in an authorized Member, rename the second `Review` to ` Coral `, then verify `Coral`/2 and the untouched first `Review`/1 through a fresh client and store connection. Exercise an authenticated caller lacking access to the target board; neither read nor edit may succeed. Demote the original Member to Viewer on an independent connection; the original client must still read but its next save must be denied, with committed rows unchanged.

Use only generated in-memory credentials; never place bearers in process arguments, URLs, logs, screenshots, handoffs or packaged fixtures. Preserve the no-network Android frame fixture. Connected fixture clients must use a real authorized caller or fail closed, with any unverified adoption explicitly recorded. No alternate anonymous host mode or test endpoint for the protected board. Keep prior gates, workspace formatting and locked tests. Check both the Android probe and the separately locked Kit app for client contract changes; list exactly which runtime journeys were exercised. Windows direct-store development mode is not an authenticated host client. Native sign-in and full client parity stay open until demonstrated. Coordinator owns the reference comparison, runner and review. Worker updates implementation, affected documentation and handoff; no commit or push.
