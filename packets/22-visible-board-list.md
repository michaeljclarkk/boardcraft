# 22-visible-board-list

List the active boards visible to the signed-in Member or Viewer. Deliver the board portion of navigation through `EditClient` and one authenticated loopback `GET /navigation/boards`. Return only `{id, workspace_id, name}` summaries. Opt the host into multi-board discovery explicitly; starting the existing single-board fixture must not advertise other boards. Keep item GET/PUT scoped to the host's configured target even when discovery is enabled. Listing an ID is not a grant to open or edit it.

The reference navigation read first takes up to 2,000 visible workspaces by position then name; within that set it takes up to 2,000 visible boards **globally** by board position then name. Use the active-only read: both parent and board must be active. Apply access filters before each limit, in PostgreSQL, without per-board queries. The sidebar selects its workspace from these results; do not group or alphabetize the wire list in the client. No reference order is defined for an exact position/name tie; a UUID tie-break for deterministic native reads is fine.

For these two roles an open workspace requires no membership. A closed workspace requires **workspace creator or workspace member**, even for a board creator/subscriber. Within an allowed workspace Main is readable; Private and Shareable require **board creator or board subscriber**. Workspace creation/membership alone does not open a private board. Resolve the in-memory bearer and current account on every request. Omit denied boards entirely; an authenticated caller with nothing visible gets `200 []`. Missing/rejected session → 401; unavailable access store → 503, never a successful empty list. Use the existing typed errors. These status codes are the loopback contract.

Reuse the host's access owner for list eligibility and the target board's read/write decision. Preserve the transaction and grant locks for writes, including a closed workspace membership when it supplies access. Migrate without converting existing packet 14 private grants to Main or making unclassified boards discoverable. A bare board/item ID or missing policy must still grant nothing. Preserve previously classified single-board reads without inventing a real workspace or display name for old records. No migration from private reference data.

Gate: two new enabled `loopback_board_access` cases using real serialized requests and a fresh `rustday_test` schema per case. Use generated, memory-only credentials. Give boards distinct UUIDs; insert out of display order. Compare exact ordered `(board UUID, workspace UUID, name)` tuples, not just counts. Use the following synthetic fixture (both users are outside the open workspace's explicit membership):

- `list_visible_boards_in_navigation_order`: open workspace: `Quartz` Main at 2, `Cedar` Shareable at 1 (Member subscribed), `Amber` Private at 1 (Member created, Viewer subscribed). Closed workspace: Viewer created the workspace; Member is initially outside. `Ash` Private at 0 subscribes both; `Pine` Main at 3; a third Private board grants neither user access. Other creators are distinct from these actors. Include an inactive board in an active workspace, a Main board under an inactive workspace and a board with no policy. Member gets **Amber, Cedar, Quartz**; Viewer gets **Ash, Amber, Quartz, Pine**. No hidden metadata, item rows or access lists in either response. Missing bearer is rejected. A normal single-board host must not return this catalog.
- `workspace_membership_changes_refresh_list_and_access`: configure `Ash` as the host's item target, with two `Review`/1 rows. The subscribed Member cannot read or rename it while outside the closed workspace (403). Add workspace membership on an independent connection: the same session lists **Ash, Amber, Cedar, Quartz, Pine**, and can read `Ash` with the edit hint. A listed non-target's item GET still returns 404. Demote to Viewer: same list, read-only `Ash`, valid rename denied. Remove membership: `Ash` and `Pine` disappear and the target read is denied, even with the old list in hand. Close the formerly open workspace without granting membership: list is now empty, session still resolves. Revoke that session: list now returns session rejection. Independently read back the committed role/grants and both unchanged ordered items/revisions around the denials; reads must not create sessions or grants. Exercise a real access-store fault in the disposable schema and distinguish it from an empty result; after repair the same valid session can list again.
