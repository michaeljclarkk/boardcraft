# 38-browser-group-archive-restore

Archive one **physical group**, keeping its roots in place. Restore that same group from its Undo message or, after leaving the board, from the existing board Archive. Both Restore controls call the same Rust operation. The group can be empty; its identity and availability must not be inferred from an item, a display label, the current selection or the first page of archived items.

**Compared fixture.** Reuse [37's board](37-browser-root-archive-restore.md) with two changes local to this fixture: set `g-20` to position 1 (tied with `g-90`), and have the Owner archive 67 individually first. At entry, board 201 is revision 2, 67 is Archived/2, there is one root receipt, and all groups are revision 1. The two active `Work` groups sort by ID at position 1, followed by `Reserve` at 2. `Retired` at 0 was already archived. Board 202 is a control.

**Command boundary.** Add preview-only POST `groups/{group-id}/archive` and `groups/{group-id}/restore` under the selected-board API. Bind board/group via path; command needs the expected **board** revision, not an operation ID, expected group revision, list of child revisions or caller-supplied role. Lock current session, role and selected-board/workspace/grants as for packet 37, then board and scoped group; commit group state and group/board revision increments together. Exact repeat at the old baseline conflicts; never automatically retry a write. The generic reference operation accepts a fresh same-state assignment and increments revisions. These narrower preview gestures require Active → Archived or Archived → Active; reject other source states, including Deleted. Do not repurpose the item receipt path. Migrate populated v8 groups with a positive revision without changing old states, grants, sessions, items or receipts.

Extend the existing board recovery read with archived group metadata under the same authorized board revision; include empty groups. Read groups in bounded pages with a read-only continuation on overflow, so a dismissed toast cannot strand a group beyond the first page. Keep the separate 100-item Archive page, totals and restore reasons intact. Preserve the 500-row active projection even after restore. During pending writes block duplicate submission; reject a late reply for another board/session. A conflict or unknown acknowledgment calls for a fresh board/recovery **read** and explicit action only if still eligible. If the POST succeeded but refresh failed, offer reload, not another POST. On 403 recheck selected access; on 401 return to sign-in without stale recovery targets.

**Required gates.** Drive real pointer/key events in owned headless Chromium; record request method, scoped path, baseline, status and count, plus rendered group IDs, order, item IDs and enabled controls. Use a **new PostgreSQL connection** at every acceptance, failure and retry boundary (including before fixing a fault). Compare both board revisions, all groups' IDs, order, names, states and revisions, all nine full item rows, existing receipts, session and grants. An expected database snapshot is independent of the response used to render the page.

- `browser_archives_and_restores_one_group`: exercise the table, including Escape, pending state, Undo, a second archive, Dismiss, reload, board Archive Restore and final reload. Check group ordering and bounded recovery on a larger fixture independently of the root page.
