# 13-account-session

Begin phase 1 at the account operation boundary. An existing active synthetic Viewer signs in by username or email (trimmed, case-insensitive lookup; password exact). A nonempty identifier advances locally without checking existence. Only submitting credentials can reject an unknown identifier or bad password; both give the same retryable rejection and create nothing. Reject empty/oversized credentials (raw limits 320/1024 UTF-16 units), disabled and passwordless accounts. No registration, bootstrap or real accounts. Use a vetted salted password verifier and OS randomness for a fresh 32-byte bearer per login; store only a digest of its encoded token with the account foreign key, never the bearer. Keep all generated passwords and tokens in memory, including in tests; redact errors, Debug and assertions. Return success only after the session commits.

Resolve from the token alone against current active-account data. Identity is the stable account ID; name, role, board, workspace and the development actor selector are not identity proofs. A signed-in Viewer has no board-write capability. Keep the backend and a small nonvisual client journey callable without a renderer; do not expose a new unauthenticated board route. Client state resolves before becoming ready after login or reopen; a connection/store fault during resume retains the token for retry but no ready account, while rejected resume clears it. Revoke just the supplied token on logout, then clear the client's session. No credential files or bundled accounts.

Gate: `cargo test --locked --workspace --test account_session` against a new schema per case in the explicit `rustday_test` database. Exercise real production operations, independent SQL connections and the client state (an in-process caller suffices). Require both enabled cases:

- `rejected_credentials_then_sign_in`: advance with an unknown identifier, then reject at password submission; reject a wrong password on a known account identically. Independently confirm zero sessions before correction. Retry successfully with padded/mixed-case lookup, resolve the same Viewer ID and read-only role. Independently check the salted password verifier and the committed token verifier/account link without printing secret values. Exercise username and email, exact password and invalid lengths/status.
- `resolve_retry_and_revoke`: reopen a fresh client with only the issued token; no cached role/actor. A real unavailable operation must not admit the client or lose the token; restore access and retry. Independently change the fixture's account role and resolve the current role under the same ID. Sign in twice, require distinct tokens, revoke one, and read back on new connections: old token rejected/cleared, other session still resolves. Disabled account cannot resume. Confirm committed verifier rows independently.

Runner also requires workspace format and locked portable tests. Update ownership, workflow register and handoff with concrete results. Track native login windows/secure storage, cookie/HTTP transport, protected board mutations across existing callers and account administration separately; do not claim these are verified by operation tests. Worker does not change runner, owner/private files or Git state. Coordinator owns the reference comparison.
