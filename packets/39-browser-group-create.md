# 39-browser-group-create

On a selected physical board, choose **New item options → New group of items**. An Owner gets an **Add group** dialog immediately, with **Group name** focused and editable (`New group`, caret at the end), colour `#579bfc`, and a proposed `g-<UUID>` that lasts for this dialog. Opening, typing, changing colour, blurring, Cancel and Escape do not create anything. Disable **Save group** for a blank trimmed name. Submit the untouched default or an edited draft, await commit and reread the board, then close the dialog. There is no automatic second editor on the new heading. The board-actions **Add group** alias calls the same editor in the reference; only the New item options entry is required here.

**Compared fixture.** Private board 201 at revision 1 has active `g-old` (**New group**, position 0, root 59), `g-z` (**Work**, 3, root 61) and `g-end` (**Reserve**, 12, empty). `g-hidden` (**Retired**, 20, root 57) is archived. Board 202 has `g-peer` (**Work**, 1, root 62). All groups and roots start at revision 1; the four roots have the same title. Read groups by `(position,id)`; labels and array offsets cannot identify the created group.

**Command boundary.** One preview-only POST under `/preview/api/navigation/boards/{board}/groups` and one named Rust create operation. Authenticate the current session and require current Owner plus selected active board/workspace access, held through commit. Accept the proposed ID, expected **board** revision, raw spelling and colour. A create always means group baseline zero, expanded, active and empty. Validate trimmed name (1–160 UTF-16 units) and six-digit hex colour server-side. Under the board lock use the active-group count at that revision; reject stale new creates with 409. Keep the grouped projection within 500 rows counting empty groups. Insert the group and advance the board revision once in the transaction. Keep colour with the saved group across reload; preserve old groups, including `main`, on populated migration. Native flat contracts stay unchanged.

Create is not an upsert. The reference treats a valid repeated create for an existing ID on the same board as a no-op **before** the stale-board check, even for different spelling. An authorized replay must neither overwrite nor append nor advance either revision. No separate receipt is needed. Boardcraft keeps its existing `(board,id)` key; a match on a different board alone is never a successful acknowledgment for this board. Broader resource-ID compatibility across boards remains open. Reconcile an uncertain response by **reading** the board and locating the proposed ID; never turn that recovery into an edit of an existing group. If only the refresh failed, offer Reload, not a second create. Ignore late completions from a departed board/session. On 403 recheck selected access, on 401 return to sign-in. Member may still add items, but Member and Viewer cannot create groups.

**Required gates.** Use actual pointer/key events in owned headless Chromium. Record POST count, path, ID, baseline and status; compare rendered identities, titles, order, counts and editor/focus with reads through a **fresh PostgreSQL connection** before/after each save, refusal, peer change, review, retry and reload. Check both board revisions, complete ordered group records, items (including hidden and foreign roots), receipts, session and grants independently of the API response.
