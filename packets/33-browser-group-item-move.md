# 33-browser-group-item-move

On selected board 201, move **one existing root item** from the first `Work` to the last `Work`. Open **More options for Ink** on UUID 61 → **Move to** → **Move selected items**. The Member's destination board stays fixed. The **Destination group** select starts at the first active group; its labels are `Work`, `Reserve`, `Work`, with values `g-90`, `g-10`, `g-20`. Choose `g-20` by identity, then **Confirm**. Selection alone and Cancel make no write. This is the table row menu, not drag-and-drop, the selection toolbar or an inline group picker.

**Reference result.** Use the [31 fixture](31-browser-board-groups.md) with one move-specific variation: `Ink` 61 and `Ink` 59 both have position 2, and 61 was created **earlier** than 59. Before: `g-90=[73 Sketch,61 Ink]`, `g-10=[]`, `g-20=[59 Ink]`. After Confirm and a document reload: `g-90=[73]`, `g-10=[]`, `g-20=[61,59]`; counts `1 item`, `No Items`, `2 items`. The existing UUID 61 retained its board, title, position, creation time and creator; only its group and its revision changed (1 → 2, group-field stamp 2). No other row changed. **Do not append, renumber or break ties by UUID alone.** The unsorted physical group page orders by source position, creation time, then item UUID. A tie on position can arise from an ordinary move even when each group had distinct positions before it.

The actual table, menu, dialog and field-save queue ran in headless Chromium with a local read/write adapter and the actor-scoped reference operations on disposable PostgreSQL. The dialog captured a single item, read its latest selection, and submitted only `groupId` as changed at the reviewed revision. Cancel sent nothing. Changing the request actor to Viewer before Confirm, and separately raising a deferred DB constraint at commit as Member, each closed the dialog with a queued failure; all five DB rows (including the inactive and sibling-board rows) and group stamps matched the baseline on independent reads. On Viewer reload **Move to** was disabled. The comparison used a queue-error display adapter, not the full signed-in shell. The board screen's recovery controls for a failed group save are **Review move**, **Apply reviewed move** and **Dismiss**; reading the latest or dismissing is not consent to write.

**Store and transport.** Add one bounded matched-browser-session `PUT /preview/api/navigation/boards/{board}/items/{item}/group` with `{group_id, expected_revision}`. No client-supplied actor, title, order or inferred grant. Reuse current selected-board write authorization and lock the existing item and the active source/destination groups **on that board** through commit. Return the committed UUID, group, title and revision only after commit. No new item, delete/reinsert, native endpoint or general bulk operation. In the [board store](../crates/board/src/store.rs), persist the last revision that changed the group. A positive known baseline may cross an unrelated rename, but cannot cross a later group change (even an intervening move back). Check this before a same-value no-op. A current request for the same group leaves position, item revision and group stamp unchanged. A missing item or revision zero must never create one. Keep provenance from [32](32-browser-group-item-create.md) and protect both create and rename gates.

Migrate v4 transactionally: permit tied positions within a group; keep a stable creation-order key and final UUID tie-breaker for both grouped and flat selected reads. Use creation time for new items; for old snapshots with no timestamp document a deterministic fallback, not invented historical dates. Existing distinct-position snapshots keep their order, names, IDs and revisions. Preserve the scoped group foreign key, the bounded grouped projection, and serialized append for new items. No nullable-position import, reordering operation or rewrite of neighbor rows in this packet.

**Recovery.** Capture the displayed item's baseline; if a fresh authorized read on dialog open finds a different group, retain the choice but require explicit review before replacement. The server must independently detect group changes after this read. While pending disable Confirm and show saving; never present changed counts as committed. On success refresh the grouped board at the same URL. On conflict, validation or fault, close the dialog, keep the failed requested group by ID with a board-level error. Review fetches the current authorized state; only explicit Apply may submit the reviewed revision. Hide Apply if the item/destination is unavailable or access is now read-only. On 403 recheck the board: demotion shows the unchanged groups read-only; loss of visibility shows Destination unavailable; 401 returns to sign-in. No automatic repeat after unknown acknowledgment, refresh failure, reload or navigation. Discard late results from a superseded visit. Persisted failure recovery across restart, live peer notifications and native UI remain open.

**Gate.** Use real headless Chromium input and the preview host. Assert method/path/status and request counts, group-local ordered UUIDs/titles and heading counts. Independently reconnect to `rustday_test` **at each failure before recovery**, and after success/reload: compare both groups, positions/order keys, item identity, title, revision, group stamp and creation provenance; include empty `Reserve`, archived 57, 202/62, the direct target, grants and the privately matched account/session. A fresh grouped GET and a flat read must agree on the committed order.
